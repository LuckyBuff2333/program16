[结果 1] WIKI 文档 [智能影像/BootAnimation.md]:
1. 背景简介
  本文将介绍开机动画功能根据应用日志分析定位问题的方法，动画的一般问题点包含标定不匹配、服务初始化失败、动画准备失败、动画播放出现中断，卡顿，掉帧，闪屏等现象、动画不退出、资源销毁失败、动画未触发播放等，下面将按照问题点分类，结合代码和日志一一拆解分析方法和典型的问题特征。
  由于高通不同平台的限制，开机动画的播放器代码实现分两种方案，对于8155芯片平台采用基于OpenMax AL框架实现的视频播放器，对于8255/8775芯片平台采用qcom原生的VIDC框架实现视频播放器，两者的核心日志差别很大，所以分析日志时除平台common问题外，其它情况下应区分具体平台，再匹配特征日志定位问题。

      动画模块初始化包括读取标定，读取json配置文件和创建视频播放器、任务调度器等对象，进程启动后只做一次，某个步骤失败都会导致动画初始化中断，动画无法播放。
      动画最终初始化成功，将打印日志：MultiScreenAnim init success.

2.3 动画播放异常
    - 分析方法
      动画触发播放后，需设置omx播放器切换至playing状态并设置子窗口可见，播放器将mp4文件一帧帧解码并post给主窗口，子窗口通过共享buffer不断刷新显示画面，从而实现单屏或多屏同帧播放动画效果。常见的播放异常现象包括动画未播放，播放中断，播放卡顿、掉帧或闪屏，播放结束后不退出，下面将对以上现象分别结合日志分析。
2.3.1 动画未播放
      - 日志TAG
        multiscreen_animation
      - 正常日志
        //接到触发播放信号
        SUSD ANIMATION PLAY DOOROPEN received, start play animation. ###Fatal###
        //设置播放器状态为playing成功
        OmxDecoder setPlayState XA_PLAYSTATE_PLAYING success. ###Fatal###
        VideoPlayer playControl success, VideoPlayState = %d. ###Fatal###
        //设置子窗口为可见成功
        WindowsManager displaySubWindows success, visible= %d. ###Fatal###
        //buffer成功post到窗口，表明动画已经播放出来
        screen post window complete, countId: %d, cost time: %ld us.
      - 异常日志
        //动画还未准备，无法播放
        animation is inactive, can not control play.
        //设置播放器为playing状态失败
        m_omxPlayerItf GetPlayState failed, res = %d.
        m_omxPlayerItf SetPlayState XA_PLAYSTATE_PLAYING failed, res = %d.
        m_pVideoPlayer playControl failed.
        //设置窗口可见失败
        WindowsManager setWindowVisible failed, window name: %s.
        screen_flush_context failed, error: %s.
        m_pWindowsManager displaySubWindows failed.
        //解码器输出buffer为空，无法被post到窗口
        currBuffer is nullptr.
        //输出buffer post到窗口失败
        screen_post_window failed, error: %s.
      - 日志分析说明
        动画不播放可能的原因有很多，首先怀疑是 1. 未接到触发信号，表明接到触发信号的日志是“SUSD ANIMATION PLAY DOOROPEN received, start play animation. ###Fatal###”，如果没有这条日志打印则说明信号未接到，应转给susd或vip check信号是否发送；2. 若以上日志打印，则可能是由于设置播放器状态异常或者子窗口设置为可见失败，导致播放loop无法运转起来或者窗口无法显示；3. 若日志表明播放器和窗口设置也正常，应继续check第一帧buffer是否正常上屏，可能解码失败buffer为空或者 buffer post到窗口失败，“screen post window complete, countId: %d, cost time: %ld us.”打印这条日志说明动画已经上屏。
        如果动画初始化或者准备阶段就已经失败了，显然也没法播放动画，因此参考章节2.1, 2.2也是动画未播放的可能原因。

2.3 动画播放异常
    - 分析方法
      动画触发播放后，需设置omx播放器切换至playing状态并设置子窗口可见，播放器将mp4文件一帧帧解码并post给主窗口，子窗口通过共享buffer不断刷新显示画面，从而实现单屏或多屏同帧播放动画效果。常见的播放异常现象包括动画未播放，播放中断，播放卡顿、掉帧或闪屏，播放结束后不退出，下面将对以上现象分别结合日志分析。
2.3.1 动画未播放
      - 日志TAG
        multiscreen_animation
      - 正常日志
        //接到触发播放信号
        SUSD ANIMATION PLAY DOOROPEN received, start play animation. ###Fatal###
        //设置播放器状态为playing成功
        OmxDecoder setPlayState XA_PLAYSTATE_PLAYING success. ###Fatal###
        VideoPlayer playControl success, VideoPlayState = %d. ###Fatal###
        //设置子窗口为可见成功
        WindowsManager displaySubWindows success, visible= %d. ###Fatal###
        //buffer成功post到窗口，表明动画已经播放出来
        screen post window complete, countId: %d, cost time: %ld us.
      - 异常日志
        //动画还未准备，无法播放
        animation is inactive, can not control play.
        //设置播放器为playing状态失败
        m_omxPlayerItf GetPlayState failed, res = %d.
        m_omxPlayerItf SetPlayState XA_PLAYSTATE_PLAYING failed, res = %d.
        m_pVideoPlayer playControl failed.
        //设置窗口可见失败
        WindowsManager setWindowVisible failed, window name: %s.
        screen_flush_context failed, error: %s.
        m_pWindowsManager displaySubWindows failed.
        //解码器输出buffer为空，无法被post到窗口
        currBuffer is nullptr.
        //输出buffer post到窗口失败
        screen_post_window failed, error: %s.
      - 日志分析说明
        动画不播放可能的原因有很多，首先怀疑是 1. 未接到触发信号，表明接到触发信号的日志是“SUSD ANIMATION PLAY DOOROPEN received, start play animation. ###Fatal###”，如果没有这条日志打印则说明信号未接到，应转给susd或vip check信号是否发送；2. 若以上日志打印，则可能是由于设置播放器状态异常或者子窗口设置为可见失败，导致播放loop无法运转起来或者窗口无法显示；3. 若日志表明播放器和窗口设置也正常，应继续check第一帧buffer是否正常上屏，可能解码失败buffer为空或者 buffer post到窗口失败，“screen post window complete, countId: %d, cost time: %ld us.”打印这条日志说明动画已经上屏。
        如果动画初始化或者准备阶段就已经失败了，显然也没法播放动画，因此参考章节2.1, 2.2也是动画未播放的可能原因。
2.3.2 播放中断
      - 日志TAG
        multiscreen_animation
      - 正常日志
        //buffer成功post到窗口，这条日志持续打印，countId不断递增
        screen post window complete, countId: %d, cost time: %ld us.
        //播放器head at end，表明已播放到最后一帧
        PlayEvent XA_PLAYEVENT_HEADATEND received, notify pause receive thread. ###Fatal###
      - 异常日志
        //解码器输出buffer为空，无法被post到窗口
        currBuffer is nullptr.
        //输出buffer post到窗口失败
        screen_post_window failed, error: %s.
      - 日志分析说明
        播放中断指已经正常播放动画了但是未到最后一帧画面就停止刷新，只有出现以下日志“PlayEvent XA_PLAYEVENT_HEADATEND received, notify pause receive thread. ###Fatal###”才能表明动画成功完整播完；动画播放中断的原因可能是 1.中途解码器输出Buffer卡住，日志不再打印countId递增；2.解码输出buffer一直为空或者post buffer到窗口一直失败。
2.3.3 卡顿、掉帧、闪屏
      - 日志TAG
        multiscreen_animation
      - 正常日志
        //buffer成功post到窗口，这条日志持续打印，countId不断递增
        screen post window complete, countId: %d, cost time: %ld us.
        //播放器head at end，表明已播放到最后一帧
        PlayEvent XA_PLAYEVENT_HEADATEND received, notify pause receive thread. ###Fatal###
      - 异常日志
        //解码器输出buffer为空，无法被post到窗口
        currBuffer is nullptr.
        //输出buffer post到窗口失败
        screen_post_window failed, error: %s.
      - 日志分析说明
        播放过程中卡顿、掉帧一般是因为窗口buffer刷新频率跟不上fps要求，当前mp4的fps是25(标准时间间隔是40ms)，1.当前后连续几帧的时间间隔超过40ms时会表现为画面卡顿或掉帧，即"screen post window complete, countId: %d, cost time: %ld us."这条日志不断打印且countId递增时，相邻两条日志的时间戳相差超过40ms；2.播放loop过程中某几帧解码异常或post window失败，会打印异常日志，表现为画面跳跃不连续的闪屏。

2.4 动画资源销毁失败
    - 分析方法

1. 背景简介
  XVR指座舱的单路或多路行车影像记录功能，将摄像头采集的图像，叠加实时水印信息(如时间，车速，档位，刹车，转向)后录制成一段段视频文件，存储在U盘，可供用户调出回放。整个功能分为两部分，qnx侧负责摄像头取流、叠加水印、硬编码和写入共享内存，安卓侧负责读取共享内存生成mp4文件、存U盘、视频回放等；本文主要针对qnx侧部分功能，介绍如何根据日志定位分析XVR功能的常见问题，一般分为：视频不录制、录制中断、视频回放异常、水印信息异常，下面将结合日志展开分析。
2. 问题汇总
2.1 视频不录制
    - 分析方法
      当用户开启录制，等待很长时间后仍没有视频生成，除安卓侧落盘异常外，对qnx侧分析可能原因是 1.qnx应用服务初始化失败，2. qnx侧应用未收到安卓侧发出的开启录制信号，或者 3. 已开启录制，但整个录制流程pipeline中间出问题，例如摄像头不出流、图像预处理失败、h264编码失败或内存共享异常等。

2.2 录制中断
    - 分析方法

      - 日志分析说明

        摄像头画面未裁剪时播放的是摄像头取流到的原图，表现为四周边界有绿色区域或者无效画面，一般是由于没有读取到视图的裁剪标定而直接采用原图录制，异常日志下获取的标定值都是0.
