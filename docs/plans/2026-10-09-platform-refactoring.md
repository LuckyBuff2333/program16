# 测试分析平台渐进重构 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 保留现有业务能力，围绕任务中心和结果审核精简导航、统一操作流程，再逐步治理任务运行和代码边界。

**Architecture:** 保留 FastAPI 单体部署和既有外部接口，渐进迁移为模块化单体。先用兼容适配层复用现有执行逻辑，再统一任务身份、事件、结果和存储边界。PC 与线上执行共享任务管理，但保留各自执行策略，不假定业务语义相同。

**Tech Stack:** 现有 Python / FastAPI / Vue 3 / Element Plus / SQLAlchemy / CSV / 飞书集成；前端组件化阶段建议采用 Vue SFC、TypeScript 和 Vite，需在实施前验证静态部署和打包兼容性。

---

## 一、已确认范围

- 优先精简页面和操作流程，不删除现有业务能力。
- 以任务中心统一执行入口，以结果审核统一结果处置入口。
- 一级导航：工作台、任务中心、结果审核、数据报表、设置与工具。
- 冒烟、回归、自动检测作为任务类型；AB 实验作为任务对比入口。
- 当前交付仅为方案，不修改业务代码，不运行可能调用真实接口的应用或测试。
- 不增加用例管理、测试计划、需求管理等全新业务，不把现有平台扩建为另一套产品。

## 三、备选方案

| 方案 | 收益 | 成本与风险 | 结论 |
| --- | --- | --- | --- |
| 仅调整菜单和名称 | 见效快，底层风险低 | 重复流程和状态机制不变 | 可作为第一阶段，不作为最终状态 |
| 统一任务与审核，渐进治理模块 | 同时改善操作和维护成本 | 需要兼容旧行为及明确任务模型 | 推荐，用户已确认产品方向 |
| 全量重写或微服务化 | 可以重建边界 | 接口、数据、部署和隐含规则迁移风险高 | 不推荐；目前没有独立扩容证据 |

## 四、目标信息架构

### 工作台

- 运行中任务、待审核数量、失败趋势、最近任务。
- 保留“新建任务”和“处理待审核”两个主操作。
- 不重复放置完整执行表单，不成为新的大杂烩页面。
- 缺数据、接口失败和有效的零值分别呈现。

### 任务中心

- 任务列表、新建任务、任务详情。
- 输入源统一：Jira 号、JQL、CSV、历史结果选择。
- 执行方式统一选择：PC / 线上，但执行策略分别实现。
- 任务类型：单次分析、批量分析、冒烟、回归、定时检测、抽查复核。
- 冒烟保存固定用例和版本参数；回归保存样本和轮次；定时检测保存 JQL、间隔及停止规则。
- AB 实验使用固定输入快照和 A/B 参数快照；若比较不同功能模块，必须提示指标不可直接等价比较。
- 提交前显示原始数量、去重数量、过滤理由和最终执行清单。
- 常用参数默认展示；模型、下载并发、分析并发、缓存策略折叠到高级参数。
- 单次执行、计划执行、失败重试共享详情页和结果表，但不混用各自规则。

### 结果审核

- 按待审核、分析失败、需要修正、已确认等视图组织记录。
- 列表展示 Bug、所属任务、执行来源、分析状态、置信度和审核状态。
- 详情抽屉展示报告、评论对比、触发时间来源、诊断证据及历史处置。
- 操作：确认、修正触发时间、重新提取、诊断、重试、显式写入。
- 结果置信度写入、人工审核结果写入和知识库入库是不同动作，权限、确认和目标分别展示。
- “无法判断”不得显示为高置信度通过；既有写入策略迁移时保留并显式标注，策略改变单独审批。
- 数据库抽查的执行属于任务中心，复核结果属于审核中心，统计属于报表。

### 数据报表

- 日/周/区间汇总、批次统计、失败类别、耗时、成功率、抽查和实验对比。
- 报表点击记录进入同一任务详情或审核详情，避免另造执行入口。
- 分开定义接口提交成功率、分析完成成功率、人工确认正确率。
- 保留 CSV 导出与飞书报表能力；不改变历史字段含义。

### 设置与工具

- 常规设置：外部接口、Mock/真实模式、字段映射、阈值和默认执行参数。
- 高级工具：Jira 字段验证、接口联调、日志可视化、缓存维护、触发时间独立工具。
- 参数调优提供任务模板配置和历史任务对比，不另建一套执行器。
- 飞书机器人、通知、播报、授权等集成入口继续保留。
- 原工具在迁移期间有明确的新入口映射；不得用“高级工具”隐藏未迁移能力。
- 真实接口写入和数据清理动作明确展示范围并要求确认；密钥不进入日志和导出。

## 六、目标技术结构

```text
用户页面
  -> API 路由与请求模型
  -> 任务服务 / 分析服务 / 审核服务 / 报表服务
  -> PC执行器 / 线上执行器 / 抽查与诊断策略
  -> Jira / AI / 飞书 / 知识库客户端与存储适配器
```

建议的新目录（不是当前已经存在的目录）：

```text
frontend/src/
  pages/             工作台、任务、审核、报表、设置
  components/        结果表、进度、参数表单、证据抽屉
  api/               普通请求与流式事件适配
  composables/       任务状态、筛选、事件订阅
src/
  web/routers/       HTTP 路由，不编排业务
  services/          tasks、analysis、reviews、reports
  models/            请求、任务、结果、审核、事件模型
  repositories/      任务状态、CSV、缓存与云表适配
  clients/           保留并复用现有外部客户端
  core/              保留纯分析、比较、文档生成能力
```

不为每个功能叠加多层抽象；只在多个真实调用方共享规则或需要替换外部依赖时建立接口。

## 七、任务与数据模型

- Task：task_id、类型、输入快照、参数快照、执行模式、状态、创建与更新时间。
- TaskItem：item_id、task_id、bugid、步骤、尝试次数、状态、错误、外部执行标识。
- AnalysisResult：分析结果、报告位置、置信度、来源、版本及关联的执行尝试。
- Review：审核状态、审核人、修正值、理由及时间；不覆盖原始证据。
- TaskEvent：event_id、task_id、item_id、类型、步骤、计数、消息和时间。
- Schedule：模板、时间规则、启停状态和上次执行；后续是否需要独立实体取决于调度实现。

任务运行状态建议：queued / running / succeeded / partial_failed / failed / cancel_requested / cancelled / interrupted。
审核状态、云表同步状态、知识库入库状态分别维护，不用一个“成功”表示全部完成。

取消按 task_id 或 item_id 定位；同一个 Bug 可在不同模式、版本和批次下执行。断开流式连接不等于取消后台任务，刷新页面通过任务状态重新订阅。

进程重启后先把遗留 running 任务标记为 interrupted，并核对外部执行状态；不能直接重发已经产生副作用的请求。取消的效果应分别记录为停止派发、已请求外部取消、等待外部结束，不承诺接口不支持的强制停止。

### 存储原则

第一阶段不改变现有数据库、CSV、飞书表格和知识库的事实源。实施前为每个字段列出所有者、读写路径、冲突规则和同步状态。

如需跨刷新和重启恢复，建议新增独立任务运行账本，而不是修改外部维护的 bug_records。单实例可评估独立 SQLite；是否使用共享数据库取决于部署实例数和并发，尚未确认。

CSV 保留为历史输入及导出产物，不全量迁移。飞书表格和知识库继续承担现有业务角色；失败同步显式标记待处理，不能显示为全部写入成功。

## 八、关键决策记录

### ADR-001：按任务和审核组织产品

- 状态：产品方向已确认。
- 背景：当前导航围绕工具名称，重复展示执行和结果处置。
- 决策：五项导航，任务与审核为主线，低频能力保留于高级工具。
- 收益：减少入口选择，形成闭环。
- 成本：需要新旧入口映射及用户适应期。
- 替代：只整理菜单；收益不足，作为过渡而非终态。

### ADR-002：模块化单体，不做微服务

- 状态：技术建议，实施前确认。
- 决策：复用 FastAPI、客户端及现有部署，先划分服务和存储边界。
- 收益：降低部署和迁移成本。
- 成本：必须用依赖约束和测试避免再次形成大文件。
- 替代：全量重写、微服务；当前缺少独立扩容需求，不采用。

### ADR-003：统一任务管理，不统一抹平执行语义

- 状态：技术建议。
- 决策：共同任务协议，PC/线上、抽查和诊断采用各自策略。
- 收益：一致的进度、恢复和取消体验。
- 成本：兼容旧事件与差异化参数。
- 替代：把所有接口强行合成一个执行函数；容易改变业务规则，不采用。

### ADR-004：数据渐进迁移，副作用显式控制

- 状态：技术建议，存储选型待确认。
- 决策：先明确事实源和幂等边界，再引入任务账本；不自动批量迁移历史数据。
- 收益：保护历史记录和真实云端数据。
- 成本：兼容期需要适配多个存储。
- 替代：立即全量迁库；回滚困难，不采用。

3. 将诊断、修正和重试串成闭环，并展示每项外部写入状态。
4. 核对历史 CSV 与新报表的字段、筛选及指标口径。
5. 更新 README 的产品定位、FastAPI 技术栈、运行入口和导航。
6. 完成能力台账验收后停用旧导航；旧 API 的停用需要单独确认调用方，不随页面删除。

交付：统一操作闭环、历史兼容和可用的项目文档。

## 十、验收标准

- 一级导航严格为已确认的五项。
- 旧能力清单的入口映射覆盖率 100%，无业务能力静默丢失。
- 新建普通分析任务最多三步：选择输入、确认执行策略、提交；高级参数不强制展开。
- 同一 Bug 记录可直接完成查看证据、修正、重试；无需手工复制到另一个工具。
- PC/线上、JQL/CSV/直接输入、冒烟/回归/自动检测均保留各自必要规则。
- 任务刷新和重新进入后显示同一后台状态；断开页面不得被误判为成功或取消。
- 同一 Bug 的两次执行有不同身份，取消一个任务不影响另一个。
- 部分失败、未判定、待审核、同步失败、入库失败分别呈现，统计口径一致。
- 重复请求及重试不造成未经确认的重复外部写入。
- CSV 历史结果仍可读取和导出；真实配置、数据库及云表不受自动测试污染。
- 对比固定输入和配置快照，迁移前后分析结果、筛选数量和目标写入一致。
- 在相同测试样本下记录性能基线；具体延迟及吞吐阈值需结合当前环境确定，不承诺未测量数字。

## 十一、风险与回滚

- 导航合并遗漏低频功能：能力台账 + 旧导航开关。
- 合并导致业务规则变化：先适配旧实现，再经独立变更审批调整规则。
- 外部接口重复调用或重复写入：输入/配置快照、尝试标识、写入台账及外部状态核对。
- 云端与本地不一致：显式同步状态及失败重试，不能用本地成功代替云端成功。
- 任务取消误伤并行任务：按 task_id / item_id 隔离取消。
- 浏览器定时任务迁移后重复调度：新旧调度器互斥，灰度仅启用一个派发源。
- 打包、Docker、离线资源回归：每阶段验证对应分发方式，不引入必须依赖外网的前端资源。
- 数据变更：先备份和演练恢复；旧存储保留，新任务账本独立，不做破坏性迁移。

## 十二、实施前尚需确认

- 单实例还是多实例部署、常用用户数和实际并发任务规模。
- 各写入目标与字段的事实源，尤其飞书表格与知识库的边界。
- 是否要求服务重启后自动续跑；方案默认先核对并标记中断，而不是盲目自动重发。
- 常用功能的实际频率和角色差异，用于验证默认界面，而非决定删掉低频能力。
