# Bug 5005 日志分析报告

## 根因结论
报表任务慢SQL未命中索引致全表扫描锁表，引发下游服务线程阻塞与雪崩。

## 问题触发时间
2026-08-13 16:20:04

## 关键日志依据
- 2026-08-13 16:18:42 [WARN] report-service - SQL 执行耗时 8.3s，语句 SELECT * FROM t_trade_record WHERE create_time > '2026-01-01'，未命中索引
- 2026-08-13 16:20:04 [ERROR] report-service - 慢SQL全表扫描 1200 万行并持有表锁，执行耗时 56s，触发锁表
- 2026-08-13 16:20:08 [ERROR] order-service - 业务线程阻塞堆积：等待 t_trade_record 行锁的线程达 210 个，线程池使用率 100%
- 2026-08-13 16:20:15 [ERROR] gateway - 下游接口 /api/trade/query 超时率 92%，根因为慢SQL锁表导致业务线程阻塞

## 分析步骤
1. **发现的问题现象**：网关层 `/api/trade/query` 接口超时率骤升至92%，订单服务业务线程池使用率达到100%，系统出现大面积请求阻塞与降级。
2. **深入排查的过程**：向上游追溯日志，发现异常始于 `report-service` 执行的查询语句；结合 `db-monitor` 日志确认 `t_trade_record` 表锁等待会话数持续攀升，判定故障源头在数据库层而非应用代码逻辑。
3. **定位到的具体根因**：定时报表导出任务触发的SQL未命中索引，对千万级数据表进行全表扫描并长时间持有锁，导致强依赖该表的交易查询接口大量线程阻塞，最终引发连锁雪崩。
4. **修复措施或建议**：DBA已紧急Kill慢查询会话并补充 `create_time` 字段索引恢复服务；后续需落实：①优化定时任务查询范围与分页策略；②配置SQL执行超时熔断与自动Kill机制；③完善慢查询实时告警与索引缺失巡检。
