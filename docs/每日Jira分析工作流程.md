# 每日 Jira 分析工作流程

## 概述

每天围绕「昨日新增、需要分析」的 Jira 走一条固定流水线：

1. **Jira 查询**：确定今天要分析多少条、还剩多少条未执行；
2. **功能测试批量执行**：负责大批量覆盖；
3. **问题排查**：对失败记录持续诊断，并写入人工审核结果；
4. **回归测试**：对昨日分析失败的 Jira 做失败重试；
5. **收口检查**：再次用 Jira 查询确认当天是否还有未执行记录。

一句话分工：

> **功能测试批量执行负责大量覆盖，回归测试负责失败重试，Jira 查询负责看当天还有多少未执行。**

---

## 一、整体流程图

```mermaid
flowchart TD
    Start([开始当天流程]) --> Query[面板 Jira 查询<br/>查询昨日新增且需要分析的 Bug]

    Query --> HasData{是否有待分析数据?}
    HasData -->|否| Done([当天无待分析任务])
    HasData -->|是| Count[得到待分析数量 N]

    Count --> Batch[功能测试 - 批量执行<br/>持续执行模式]
    Batch --> SetBatch[按数量设置批次<br/>批次数 = ceil(N / 每批数量)]
    SetBatch --> Run[等待所有批次执行完成]
    Run --> Sink[(分析结果写入<br/>数据沉淀表)]

    Sink --> Trouble[问题排查<br/>筛选分析失败记录]
    Trouble --> Diag[持续排查<br/>视频 / 图片 / 评论区 / gmlogger]
    Diag --> Review[写入人工审核结果<br/>到数据沉淀表]

    Review --> Failed[提取昨日分析失败的 Jira 号]
    Failed --> Regression[回归测试<br/>失败 Jira 重新执行]
    Regression --> RegDone[等待回归执行完成]

    RegDone --> Recheck[再次 Jira 查询<br/>检查当天还有多少未执行]
    Recheck --> Remain{还有未执行?}
    Remain -->|有| Batch
    Remain -->|无| Done
```

---

## 二、各步骤说明

### 1. Jira 查询

**目的**：确定当天的工作量。

- 查询条件：昨日新增、且需要分析的 Bug；
- 输出：
  - 待分析总数 `N`；
  - 具体 Jira 列表；
  - 当天剩余未执行数量。

**作用**：

- 决定功能测试批量执行要覆盖多少条；
- 当天收口时再次查询，确认是否还有遗漏。

---

### 2. 功能测试 - 批量执行

**目的**：大批量覆盖待分析 Jira。

- 使用「持续执行」模式；
- 根据 `N` 设置批次，确保刚好覆盖：
  - 每批数量：`B`
  - 批次数：`ceil(N / B)`
  - 最后一批：`N - B × (批次数 - 1)`
- 等待所有批次执行完成。

**输出**：

- 每条 Jira 的 `分析结果`；
- `分析完成时间`、耗时、错误信息；
- 写入数据沉淀表。

**职责**：

> 负责大量覆盖，不负责失败重试。

---

### 3. 问题排查

**目的**：对分析失败的记录做诊断，并沉淀人工结论。

- 从数据沉淀表筛选 `分析结果 = 失败`；
- 按问题分类持续排查；
- 重点检查：
  - 视频 OCR 时间；
  - 图片 OCR 时间；
  - 评论区时间；
  - gmlogger / 压缩包 / main.log 参考时间；
- 排查完成后，把人工审核结果批量写入数据沉淀表。

**常见分类**：

| 分类 | 处理方向 |
|---|---|
| 触发时间问题 | 修正触发时间 |
| 无时间信息 | 视频/图片/评论区均无时间 |
| 无参考 | 有时间但没有抓包参考 |
| 无gmlogger | 没有可分析日志 |
| 解压问题 | 压缩包/格式问题 |
| 待人工排查 | 仍需人工确认 |

---

### 4. 回归测试

**目的**：对昨日分析失败的 Jira 做失败重试。

- 从数据沉淀表提取昨日 `分析结果 = 失败` 的 Jira 号；
- 使用回归测试重新执行；
- 等待回归执行完成；
- 回归结果继续写回数据沉淀表。

**职责**：

> 负责失败重试，不负责首次大批量覆盖。

---

### 5. 收口检查

回归完成后，再次使用 Jira 查询：

- 当天还有多少未执行；
- 是否有新增待分析；
- 是否有遗漏 Jira。

如果还有未执行：

```text
Jira 查询 → 功能测试批量执行 → 问题排查 → 回归测试 → 再查询
```

直到当天待分析 Jira 全部有结果。

---

## 三、职责边界

| 模块 | 主要职责 | 输入 | 输出 |
|---|---|---|---|
| Jira 查询 | 看昨天新增多少、今天还剩多少 | JQL / 昨日新增 Bug | 待分析数量、剩余数量 |
| 功能测试批量执行 | 大批量覆盖 | 待分析 Jira 数量 | 分析结果、数据沉淀记录 |
| 问题排查 | 失败诊断与人工结论 | 分析失败记录 | 问题分类、人工审核结果 |
| 回归测试 | 失败 Jira 重试 | 昨日失败 Jira | 回归分析结果 |

---

## 四、每日检查清单

- [ ] Jira 查询确认昨日新增待分析数量
- [ ] 功能测试按数量设置批次并执行完成
- [ ] 分析结果已写入数据沉淀表
- [ ] 问题排查已覆盖失败记录
- [ ] 人工审核结果已写回
- [ ] 昨日失败 Jira 已走回归测试
- [ ] 再次 Jira 查询确认无未执行记录

---

## 五、核心原则

```text
Jira 查询  = 看范围、看剩余
功能测试  = 大量覆盖
问题排查  = 失败归因、人工审核
回归测试  = 失败重试
```

只要每天按这个顺序执行，并保证最后 Jira 查询没有未执行记录，当天的分析覆盖就闭环了。

## 数据更新（回归测试）

- 位置：回归测试 → 数据更新。
- 按 `分析开始时间` 范围 + 来源（线上/PC）查询。
- 列出“失败后同 Jira 同来源又成功”的失败记录。
- 展示错误分类、人工审核结果、失败/成功时间。
- 支持勾选删除或全选删除；成功记录不删。

## 问题排查：同来源成功过滤

- 勾选“过滤同来源已成功”后，查询会自动把同 Jira、同触发来源已有成功记录的失败行移到“同来源已有成功记录”表；成功记录按全量查询，不受本次时间窗口限制。
- 第二个表只保留没有同来源成功记录的失败行。
- 页面显示“同来源已成功过滤 N 个”。

## 按批次排查

- 批次 Jira 不再按批次开始时间丢弃数据沉淀记录，避免数据沉淀晚于批次文档生成时“只有批次、没有排查内容”。
- 勾选“过滤同来源已成功”时，同 Jira 同来源已有成功的失败行从批次表移除，并显示过滤数量。
- 数据沉淀尚未同步时，错误信息回退显示批次文档里的备注。
