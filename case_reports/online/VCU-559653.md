## 分析结论
- **根因**: 语音助手（VA）车控拒绝播报的**文案配置资源中，"行""车"二字被误写为康熙部首字符**（`⾏`=U+2F8F、`⻋`=U+2ECB），而非标准汉字（`行`=U+884C、`车`=U+8F66）。TTS 引擎无法合成康熙部首字符，导致"车"字发音丢失，用户听到的播报缺少"车"字。

- **因果链**: 
  1. 副驾 VA 指令"打开方向盘加热" → 权限校验判定副驾无权（`exeResult:16001`，拒绝行为正确）
  2. NLG 从配置资源读取拒绝文案 → 文案中"行""车"为康熙部首字符（源头数据错误）
  3. voice server 下发该文案至 TTS（`hatch tts -> 为保障⾏⻋安全，这个让主驾来说吧`）
  4. TTS 引擎无法合成部首字符 `⻋` → "车"字发音丢失
  5. 用户听到"为保障行车安全，这个让主驾来说吧"（缺"车"字）

- **关键证据**:
  - **异常文案原文**（多 PID 一致）：`hatch tts -> 为保障⾏⻋安全，这个让主驾来说吧`（PID 5439，12:03:41.142 等多次）
  - **强负向证据**：全库 1,532,815 行搜索标准汉字 `保障行车安全` → **零匹配**；而部首版本存在 → 证明源头数据即错误，排除运行时转换/日志编码产物
  - **同链路对照**：同一 `exeResult:16001` 拒绝逻辑下 `只能主驾控制哦`、`请让主驾帮你吧` 均为标准汉字且播报正常 → 排除 TTS 引擎通用缺陷
  - **影响范围扩大**：HMI 界面文本 `⽆需唤醒，说出快捷指令直接执⾏`（`⽆`=U+2F46、`⾏`=U+2F8F）同样含部首字符 → 属系统级/全局性字符编码/录入问题

- **置信度**: **high**
  - 根因（部首字符导致 TTS 缺字）有直接日志证据，且通过"标准汉字零匹配"+"同链路对照"双重验证
  - 拒绝逻辑（16001）正确，与编码问题相互独立

- **未确认项**:
  1. **具体配置文件/资源包路径与写入点**：日志内无资源加载路径信息（`hatch` 相关日志已饱和，属负向证据），需在代码/资源库侧核查 VA 文案配置源文件
