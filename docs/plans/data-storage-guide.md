## 二、各阶段交付物存储明细

### 阶段一：测试设计中心 —— "准备可执行、可信的数据集"

| 交付物 | 当前存储 | 存储格式 | 存储策略 |
|--------|---------|---------|---------|
| **JQL 搜索候选列表** | 不落盘，仅在内存中传递 | JSON（API 响应） | **无需持久化**——候选列表是中间态数据，每次实时查询 Jira 保证新鲜度 |
| **CSV 导入源文件** | `data/unanalyzed/` | CSV | **保留原始文件**，供后续追溯导入来源；定期归档 |
| **去重过滤结果** | 不落盘，仅在内存中传递 | JSON（API 响应） | **无需持久化**——过滤结果依赖多维表格实时状态，下次执行时重新计算 |
| **触发时间** | 飞书 Bitable（主）<br>`data/trigger_times/`（降级） | Bitable 记录<br>CSV | **云端优先**，本地 CSV 为降级兜底；按日期命名 `trigger_times_{日期}.csv` |
| **抽样结果** | 不落盘，仅在内存中传递 | JSON（前端 state） | **无需持久化**——抽样是临时操作，结果直接进入执行阶段 |
| **自学习记录** | `data/timestudy/` | CSV + JSON | **本地持久化**，`records.csv` 追加写入，`error_patterns.json` 覆盖更新 |

**建议：**
- 触发时间是设计阶段**唯一需要持久化**的核心交付物，因为它跨阶段传递（设计 → 执行）且提取成本高
- 飞书 Bitable 作为主存储的优势：支持多端查看、前端直接读写、支持批量操作
- 本地 CSV 降级保证网络异常时不丢失数据

---

### 阶段二：测试执行中心 —— "稳定可靠的完成单条与批量分析"

| 交付物 | 当前存储 | 存储格式 | 存储策略 |
|--------|---------|---------|---------|
| **AI 分析报告** | `docs/{日期}/{bugid}.md` | Markdown | **按日期归档**，文件名为 Jira 号；飞书云盘同步一份在线版 |
| **批次执行记录** | `docs/{日期}/batch_{时间戳}.csv` | CSV | **每次批量执行生成独立文件**，命名含时间戳防冲突；上传飞书云盘备份 |
| **每日结论报表** | `docs/{日期}/{日期}_daily.csv` | CSV | **每日一份**，追加模式写入（同一天的数据合并到一份）；刷新时覆盖更新 |
| **评论分析文档** | `docs/{日期}/{bugid}_comments.md` | Markdown | **按置信度分类存储**到 `True/` 或 `False/` 子目录，方便快速筛选 |
| **Rootcause** | 写入每日结论 CSV | CSV 字段 | 不单独存储，作为 CSV 的一列随报表持久化 |
| **置信度** | 写入每日结论 CSV | CSV 字段 | 同上 |
| **知识库入库记录** | `data/bug_records.db`（kb_analysis 表） | SQLite | 人工确认后才写入，含 bugid + 触发时间 + 根因结论 + 分析步骤 |
| **飞书在线报告** | 飞书云盘文档 | 飞书 docx | 批量执行完成后自动上传，标题含日期和成功率 |

**建议：**
- `docs/` 目录是执行阶段的**核心产出仓库**，所有分析文档和执行记录都在此按日期归档
- 评论文档的 `True/` `False/` 分类是**以置信度为分界线**的物理隔离，方便后续抽查优先关注 False 目录
- SQLite 的 `kb_analysis` 表是入库记录的**唯一权威源**，抽查评估直接从这里抽样

### 阶段三：缺陷反馈中心 —— "分析结果的深度诊断、验证、修正与回写闭环"

| 交付物 | 当前存储 | 存储格式 | 存储策略 |
|--------|---------|---------|---------|
| **诊断结果缓存** | `data/troubleshoot/{bugid}.json` | JSON | **按 bugid 独立文件**，支持增量更新（修正时间/备注/分类）；状态字段标记 `corrected`/`success` |
| **修正后的触发时间** | 飞书 Bitable（主） | Bitable 记录 | 修正后立即写回 Bitable，覆盖原值；诊断缓存中同步标记 `verify_status=corrected` |
| **修正备注/人工根因** | `data/troubleshoot/{bugid}.json` | JSON 字段 | 追加到诊断缓存中，不单独建文件 |
| **验证结果（三字段）** | 回写到 `docs/{日期}/` 的 CSV | CSV 行更新 | 找到 bugid 所在的 CSV 文件，原地更新 rootcause/AI评论总结/结果置信度 三个字段 |
| **多维表格回写** | 飞书 Bitable | Bitable 记录 | 支持 dry-run 预览后再实际写入，避免误操作 |
| **审核结论** | 飞书 Bitable | Bitable 字段 | 批量写回，支持 `only_empty_review` 避免覆盖 |
| **触发时间问题导出** | `data/troubleshoot/trigger_time_issues/` | CSV | 本地 CSV + 上传飞书云盘，供团队协同排查 |
| **视频/帧/OCR 临时文件** | `data/` 下临时目录 | 二进制/图片 | **可清理**，仅在诊断过程中使用，诊断完成后无保留价值 |

**建议：**
- 诊断缓存用 JSON 而非 SQLite，因为**诊断数据结构灵活**（不同 Bug 的诊断字段可能不同），JSON 天然支持 Schema-free
- 验证结果**回写到原 CSV**而非新建文件，保证数据一致性——查看报表时看到的就是最新校正值
- 多维表格是团队协作的**唯一事实源**（Single Source of Truth），审核结论、触发时间修正都以多维表格为准

### 阶段四：质量分析与决策 —— "多维度质量报告，支撑评估、优化和改进决策"

| 交付物 | 当前存储 | 存储格式 | 存储策略 |
|--------|---------|---------|---------|
| **每日汇总统计** | 不落盘（实时计算） | JSON（API 响应） | 从每日结论 CSV 实时聚合，无需额外存储；如需持久化可上传飞书文档 |
| **周报/时间段汇总** | 不落盘（实时计算） | JSON（API 响应） | 同上，按需生成 |
| **抽查审核总表** | `reports/audit_comparison.csv` | CSV | **全局唯一文件**，每次抽查追加；含新旧对比详情供人工复核 |
| **不达标抽查报表** | `reports/audit_failed_{日期}.csv` | CSV | **按日期独立文件**，方便追溯历史不达标记录 |
| **已抽查记录** | `reports/audited_bugids.csv` | CSV | **全局唯一文件**，追加写入；下次抽查自动排除已抽过的 bugid |
| **重新分析文档** | `reports/spotcheck/{日期}/re-{bugid}.md` | Markdown | **按日期归档**，文件名含 `re-` 前缀区分正常分析 |
| **抽查审核表（日期版）** | `reports/spotcheck/{日期}/audit_comparison.csv` | CSV | 每次抽查在对应日期目录下也生成一份，方便按日期查看 |
| **调优分析结果** | 不落盘（实时计算） | JSON（API 响应） | 从批次执行 CSV + 多维表格实时聚合 |
| **数据看板** | 不落盘（前端渲染） | Vue 组件 | 从 API 实时获取，数据源分散在 CSV + Bitable + 云盘 |

**建议：**
- `reports/` 目录**专注质量分析产出**，与 `docs/`（执行产出）物理隔离，职责清晰
- 抽查的三份文件（审核总表、不达标报表、已抽查记录）是**质量门禁的核心证据**，需长期保留
- 汇总统计（日报/周报/调优）实时计算而非预计算，因为数据源（CSV）会被校正回写更新，预计算会导致数据不一致

## 三、存储位置决策矩阵

| 数据特征 | 推荐存储 | 理由 |
|---------|---------|------|
| **需要多端协作查看** | 飞书 Bitable | 支持 Web 端查看/编辑、API 批量读写、权限控制 |
| **需要团队共享的文档** | 飞书云盘 | 支持在线预览、链接分享、版本管理 |
| **结构化分析结果** | 本地 CSV（`docs/{日期}/`） | 轻量、pandas 友好、Git 可追踪变更 |
| **非结构化长文档** | 本地 Markdown（`docs/{日期}/`） | 可读性好、支持代码高亮、Git diff 友好 |
| **灵活的运行时缓存** | 本地 JSON（`data/`） | Schema-free、读写快、支持增量更新 |
| **需要事务保证的结构化数据** | SQLite（`data/bug_records.db`） | ACID 事务、SQL 查询、零配置 |
| **临时中间数据** | 内存（不落盘） | 用完即弃，避免磁盘垃圾 |
| **运行日志** | `logs/{类型}_{日期}.log` | 按天滚动、便于排查问题、定期清理 |

## 五、治理建议

### 5.1 生命周期管理

| 数据类型 | 保留策略 | 清理方式 |
|---------|---------|---------|
| `docs/{日期}/` 分析报告 md | **永久保留** | 不主动清理，作为历史分析证据 |
| `docs/{日期}/` 批次 CSV | **永久保留** | 不主动清理，作为执行记录 |
| `docs/{日期}/` 每日结论 CSV | **永久保留** | 不主动清理，作为质量追溯依据 |
| `data/troubleshoot/*.json` | **保留 90 天** | 定期归档超过 90 天的诊断缓存 |
| `data/timestudy/` | **永久保留** | 追加写入，数据量小无需清理 |
| `reports/spotcheck/` | **永久保留** | 抽查证据需长期可追溯 |
| `logs/` | **保留 30 天** | 定期清理过期日志 |
| 飞书 Bitable 记录 | **永久保留** | 云端存储不占本地空间 |
| 视频/帧/OCR 临时文件 | **诊断后即清理** | 自动清理或定期清理 |

### 5.2 备份策略

| 存储位置 | 备份方式 | 频率 |
|---------|---------|------|
| `docs/` 目录 | Git 提交 + 飞书云盘同步 | 每日 |
| `data/bug_records.db` | Git LFS 或定期拷贝 | 每周 |
| `reports/` 目录 | Git 提交 | 每次抽查后 |
| 飞书 Bitable | 飞书自带版本管理 | 自动 |
| 飞书云盘 | 飞书自带回收站 | 自动 |

### 5.3 数据一致性保障

| 场景 | 一致性策略 |
|------|----------|
| 触发时间修正 | **Bitable 为准**，本地 CSV 为降级兜底；修正后立即写回 Bitable |
| 验证结果回写 | **原地更新 CSV**，不新建文件；多维表格同步更新 |
| 审核结论 | **Bitable 为唯一事实源**，`only_empty_review` 防止覆盖 |
| 每日结论报表 | 刷新时从批次记录 + 多维表格**重新拼接**，避免增量更新遗漏 |
| 抽查排除 | `audited_bugids.csv` 追加写入，抽查前读取全集排除 |
