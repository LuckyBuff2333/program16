# log-review-pan-scan

日志分析会话复核 + 日志包泛解析 + 知识沉淀 一体化技能包。

## 这是什么

分析型 Agent（日志判读/故障定位类）的运行有一个结构性盲区：**它是目标驱动深挖的**——只为回答当前问题检索（断点附近、相关 TAG），没理由看的东西永远不会进入它的视野。后果是：

- **复核它的分析**（对不对、缺什么知识）缺少独立工具
- **知识沉淀只能沉淀"哪里坏了"**（结论性知识），沉淀不了"系统怎么运转"（构成性知识）

本技能包补这条链：**反查定位 → 会话复核（对账+挖缺口）→ 泛解析（域定向广扫）→ 按原则沉淀知识**。

| 场景 | 输入 | 能力 | 产出 |
|---|---|---|---|
| 一：反查定位 | traceId / record_id / session_id | 拉记录全量匹配，输出记录摘要与指标 | record_id + session_id + 摘要 |
| 二：会话复核 | traceId + **人工结论**（根因/问题模块） | 导出取证包，三问对账 | 复核报告（模块对账/根因对账/知识缺口清单） |
| 三：泛解析 | 日志包 + 缺口关键词 | 下载解包 + 域定向广扫 | 知识素材清单（TAG 分桶/去重样本/对照） |

场景三的产出经**知识沉淀原则**（`references/knowledge-principles.md`，17 条正本）过滤后成为知识件（架构文档/数据字典行/案例档案）。

## 环境要求

- python3.10+，`pip install -r requirements.txt`（仅 requests）
- 泛解析 fetch 需要：`curl` + `7z`（rar/zip；Linux 安装 p7zip-full/p7zip-rar）
- 凭据（环境变量，不打印不落盘）：
  - `ADP_API_KEY` —— 平台 API Key
  - `ADP_APP_ID` —— 目标应用 ID
  - `ADP_SPACE_ID` —— 应用归属空间 ID（缺失会报"应用不存在"）

  也可用 `--env-file` 指向 .env 文件注入。

## 快速开始

```bash
# 1) 反查一个 traceId（拿记录摘要）
python3 scripts/record_lookup.py <traceid> --env-file <.env>

# 2) 导出复核取证包（结论侧 + 过程侧）
python3 scripts/record_lookup.py <traceid> --env-file <.env> --export ./evidence

# 3) 泛解析（先复核、确认缺口密集后再做，见触发判据）
python3 scripts/pan_scan.py fetch --case-id <CASE-ID> --url <日志包URL> [--url <分卷2>]
python3 scripts/pan_scan.py scan --case-dir var/dl_<CASE-ID> \
    --kw "关键词|正则|组1" --kw "组2" --out pan_materials.md
```

## 典型工作流

```
用户给出 traceId + "我认定的根因/模块是…"（复核必需的两样语义输入）
  └─ 阶段1-2：反查 + 导出取证包
       ├─ record.json        → 智能体的结论（answer）与 Token/延迟基线
       └─ session_messages.txt → 分析过程（检索动作/犹豫/降级声明——缺口只藏在这里）
  └─ 阶段3：三问复核
       ├─ 模块对账（四档裁决：一致/词汇差异同一实体/环节对主模块错/错）
       ├─ 根因对账（四档裁决；对账双向——智能体的反证可能推翻人工结论）
       └─ 知识缺口清单（缺什么/过程证据/质量影响/效率影响）
  └─ [用户拍板] 缺口密集且域值得沉淀 → 阶段4：泛解析
       └─ 素材清单 → 过知识沉淀原则过滤（见下）→ 人工审核 → 入库
```

**泛解析触发判据**（三条全中才值得做，由使用者拍板，不自发触发）：
1. 冷域——知识库检索零命中
2. 高频域——平台级/多场景共享实体（一次沉淀受益面乘 N）
3. 缺口密集——多条缺口只有日志语料能填

## 知识沉淀原则（速记）

唯一正本在 `references/knowledge-principles.md`（17 条 + 素材过滤流程），本节只给速记：

- **知识库叙述系统正常运行的样子；个案发生了什么，归案例与待确认清单**
- 写作视角=业务方本人（不是分析取证视角）；取证语言不入本体
- 应有态三禁令：禁个案观测写成系统事实（尤其待判缺陷）/ 禁失败分支日志行代替机制叙述 / 禁未确认码表占位
- 自检句："这句话在系统正常运行时也成立吗？"
- 词汇桥（报单用语↔日志语言映射）是最高价值产出；具体 ID/错误码归数据字典表，禁进文档正文
- **入库动作即人工审核闸——素材清单/机器草稿禁自动入库**

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 反查报"应用不存在"（450011） | `ADP_SPACE_ID` 未设置——三个环境变量缺一不可 |
| 刚产生的 traceId 反查未命中 | 记录缓存 1 小时，加 `--refresh` 强制重拉 |
| 记录太多漏扫 | `--days` 缩窗分次反查 |
| messages 拉取退出码非 0 | 超大链路平台可能截断，消息流可能不全（取证包会带警告） |
| fetch 解包报 Unsupported Method | 个别二进制分区用了特殊压缩，日志文件不受影响，可忽略 |
| 消息 100+ 条是不是异常 | 正常——单轮 Agent 运行的工具调用+返回各算一条，不是对话轮数 |
| 素材清单能直接入库吗 | 不能——必须过 `references/knowledge-principles.md` 过滤流程 + 人工审核 |
