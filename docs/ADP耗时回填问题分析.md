# ADP 耗时回填问题分析与修复

## 一、结论

VCU-458373、VCU-525937 的耗时错误不是同一个原因：

| Jira | 错误值 | 正确值 | 根因 |
|---|---:|---:|---|
| VCU-458373 | 4.8 | 10.8 | 成功记录被后来的取消记录覆盖，状态、耗时、traceid 来自不同尝试 |
| VCU-525937 | 5.6 | 23.6 | 把模型 token 活跃耗时当成了整次执行耗时 |

更深层的问题是：**ADP 结果按 Jira 单行写回，没有按“尝试”隔离；多个字段分多次写，成功/失败/取消会互相覆盖。**

---

## 二、VCU-458373 详细分析

### 2.1 实际执行记录

ADP 历史记录里有两次执行：

| 顺序 | session | traceid | 结果 | 耗时 |
|---|---|---|---|---|
| 第 1 次 | `b3bc573c...` | `c432d1f4...` | 成功，产出 HTML | 10.8 分钟 |
| 第 2 次 | `de916cf6...` | `919beee1...` | 用户取消，无 HTML | 4.8 分钟 |

### 2.2 表格现状

修正前：

```text
完成状态 = 完成          ← 来自第 1 次成功
traceid = 919beee1...    ← 来自第 2 次取消
耗时 = 4.8               ← 来自第 2 次取消
```

所以出现“成功状态 + 取消 traceid + 取消耗时”的错位。

### 2.3 根因

1. ADP 表按 `Jira号` 定位记录，不按 `traceid/session` 定位；
2. 第 1 次成功先写入状态、traceid、耗时；
3. 第 2 次取消后又按同一个 Jira 写回，覆盖了 `traceid` 和 `耗时`；
4. 旧逻辑只保护了“耗时”，没有保护整条成功记录；
5. 后续耗时审计又按“最新 session”取了取消记录，进一步把 4.8 写了进去。

本质：**一条 Jira 只有一个记录槽位，却承载了多次尝试的字段。**

### 2.4 已修正

```text
完成状态 = 完成
耗时 = 10.8
traceid = c432d1f4...
```

## 三、VCU-525937 详细分析

### 3.1 实际执行记录

批次记录：

```text
2026-11-04 15:41:53 → 2026-11-04 16:05:28
= 23.6 分钟
```

ADP 会话记录：

```text
trace_id = 3a0314b8...
total_token_latency = 338266 ms
= 5.6 分钟
```

### 3.2 表格现状

修正前：

```text
耗时 = 5.6
```

### 3.3 根因

`total_token_latency` 是模型生成阶段的活跃耗时，不是这次分析从开始到结束的总耗时。

当前存在两套时间口径：

- `total_token_latency`：模型 token 活跃时间，约 5.6 分钟；
- 批次/会话执行时间：15:41:53 → 16:05:28，约 23.6 分钟。

耗时回填时错用了第一套口径，导致表格偏小。

### 3.4 已修正

```text
耗时 = 23.6
```

数据表和回归测试-第四批次都已修正。

## 四、进一步排查发现的其他问题

### 4.1 成功记录没有整体保护

原逻辑只保护成功耗时：

```text
已有完成记录 + 新失败 → 保留旧耗时
```

但 `traceid`、`traceid排查`、报告链接、完成状态仍可能被后续失败/取消覆盖。

**已修复：** 已有完成记录时，后续失败/取消整条记录跳过，不写任何字段。

### 4.2 最终耗时在写表之后才刷新

`run_adp_single()` 中：

1. 先设置一次耗时；
2. 再写飞书表；
3. 最后 `_stamp_elapsed()` 再刷新一次。

**已核对：** 当前主链路在写表前会执行最终 wall time 覆盖，因此正常成功/失败路径写入的是最终耗时；最后的 `_stamp_elapsed()` 只刷新内存结果，不再回写表格。

但提前返回、外部直接写回等分支仍可能绕过最终覆盖，建议后续把最终耗时显式传入写表函数，避免新分支再次引入口径不一致。

### 4.3 token 耗时与执行耗时混用

`total_token_latency`、SSE 首尾时间、批次开始/结束时间、`分析耗时` 字段口径不同。

当前至少存在：

- 模型 token 活跃时间；
- 单次 ADP 进程耗时；
- 批次任务开始到结束；
- 数据沉淀里的 `分析耗时`（纯数字按分钟处理）。

混用会造成 5.6 / 23.6 这类差异。

**建议：**

- 表格展示“执行耗时”时，统一用任务开始到结束；
- token 耗时只用于模型性能分析，不写入任务耗时；
- 后端字段名明确区分 `执行耗时` 和 `模型耗时`。

### 4.4 一条 Jira 多条数据沉淀记录

VCU-564329 等 Jira 在数据沉淀中存在两条记录：

- 一条无人工审核；
- 一条有人工审核。

日报已做去重，但数据沉淀本身仍保留重复记录。后续审计、回填如果按“最新 session”或“最新完成”取值，仍可能取错。

**建议：**

- 数据沉淀按 `jira号 + traceid` 唯一；
- 或明确只保留最后一次成功记录；
- 清理历史重复记录。

### 4.5 批次总耗时包含失败/取消

`apply_adp_batch_total()` 会把批次内所有结果耗时相加，失败/取消也可能被计入，导致 `总耗时(分)` 偏大。

**建议：** 只统计成功执行的耗时，或单独拆分“成功耗时/失败耗时”。

### 4.6 审计脚本按最新 session 取数

之前全量审计时使用“最新 session 的 token 耗时”，会：

- 优先取到取消记录；
- 用 token 活跃时间代替执行时间；
- 只改耗时，不改状态/traceid，产生错位。

**建议：** 审计必须先按状态选成功记录，再按执行起止时间取值，状态、traceid、耗时一起更新。
