## 一、测试设计中心

> **核心目标：** 准备可执行、可信的数据集
>
> 确保测试活动有据可依、目标明确；避免盲目测试，提升测试覆盖率与有效性。

### 整体流程链路

```
测试用例管理 → 候选集管理 → 数据筛选 → 抽样与时间准备
```

### 1.4 抽样与时间准备

| 维度 | 说明 |
|------|------|
| **必要性** | AI 日志分析接口需要一个精确的"触发时间"（日志分析起始时间点），否则无法定位到正确的日志片段。触发时间提取是整个流程的前置关键步骤——**没有触发时间，后续分析无法进行**。同时面对大规模候选集，需要按指定数量随机抽样控制执行规模。 |
| **流程** | **抽样：**<br>① 从可用列表中按指定数量随机抽取<br>② 优先抽取云端已有触发时间的记录（减少提取开销）<br>③ 不够时从待提取池中逐批提取<br><br>**触发时间提取：**<br>① 云端缓存命中 → 直接使用<br>② 视频附件 OCR 提取（可选兜底，2路并发保护）<br>③ Jira 评论正则匹配提取<br>④ 提取为空则标记空标记，避免重复提取<br>⑤ 每 20 条批量写入飞书 Bitable 持久化 |

| **输出** | 抽样后的 Jira 号列表 + 每个 Bug 的触发时间 + 提取来源统计（云端命中/新提取/空标记/无gmlogger） |

### 2.2 结果补全

| 维度 | 说明 |
|------|------|
| **必要性** | 批量执行只完成了"AI 日志分析"这一步，生成的 CSV 报表中 AI 评论总结、rootcause、结果置信度三个字段为空。结果补全负责对这些缺失字段进行补充填充，使每条记录达到"信息完整"状态，为后续缺陷反馈提供充足数据。**没有补全，报表数据残缺，无法进行质量分析。** |
| **流程** | ① 读取当日 CSV，识别字段不完整的行<br>② 按依赖顺序逐字段补充：<br>  **触发时间** → 从 Jira 评论提取（若缺失）<br>  **AI 分析结果** → 调用 AI 接口 / 从飞书下载文档<br>  **Rootcause** → 从 Jira issue 提取根因字段<br>  **AI 评论总结** → 全量评论 → LLM 简化 → 评论分析 → 核心语义概括<br>  **结果置信度** → 语义相似度计算（根因对比 + 步骤对比）<br>③ 每步失败不阻断后续步骤<br>④ 按置信度将评论文档分类到 `True/` 或 `False/` 目录 |
| **输入** | 不完整的 CSV 行（含 jira号 + 部分已有字段） |
| **输出** | 完整 6 列记录（jira号、分析问题时间、AI分析结果、AI评论总结、rootcause、结果置信度）+ 评论分析 md 文档 |

## 三、缺陷反馈中心

> **核心目标：** 分析结果的深度诊断、验证、修正与回写闭环
>
> 建立"问题发现 → 定位 → 修正 → 验证"的闭环机制，防止缺陷遗漏或误判，提高分析准确性。

### 整体流程链路

```
诊断中心 → 结果校正 → 审核回写
```

---

### 3.1 诊断中心

| 维度 | 说明 |
|------|------|
| **必要性** | AI 日志分析可能产生不准确的结论（触发时间偏差、日志不完整、模型误判等）。诊断中心提供深度排查能力，通过视频附件检查、gmlogger 解析、OCR 识别等多维度手段验证和修正触发时间，从而间接提升 AI 分析的准确性。**没有诊断环节，错误数据将直接流入质量评估，导致决策偏差。** |

### 关键设计原则

| 原则 | 说明 |
|------|------|
| **不自动入库** | AI 分析结果只生成文档与报表，知识库入库由人工确认后手动触发 |
| **每步失败不阻断** | 补充流程中单步失败不影响后续步骤执行，最大化数据完整度 |
| **人+AI 协同** | AI 负责初筛和自动化，人工负责校准和确认，两者互补 |
| **数据驱动闭环** | 每个中心的输出是下一个中心的输入，形成完整的数据闭环 |
| **信任但要验证** | 通过随机抽查复核验证 AI 分析的可靠性，量化误判率 |
