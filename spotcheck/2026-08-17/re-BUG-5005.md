# Bug BUG-5005 日志分析报告

## 根因结论
慢SQL全表扫描未命中索引引发锁表，导致下游服务线程阻塞与接口大面积超时。

## 问题触发时间
2026-08-13 16:20:04

## 关键日志依据
- 2026-08-13 16:20:04 [ERROR] report-service - 慢SQL全表扫描 1200 万行并持有表锁，执行耗时 56s，触发锁表
- 2026-08-13 16:20:08 [ERROR] order-service - 业务线程阻塞堆积：等待 t_trade_record 行锁的线程达 210 个，线程池使用率 100%
- 2026-08-13 16:20:15 [ERROR] gateway - 下游接口 /api/trade/query 超时率 92%，根因为慢SQL锁表导致业务线程阻塞
- 2026-08-13 16:18:42 [WARN] report-service - SQL 执行耗时 8.3s，语句 SELECT * FROM t_trade_record WHERE create_time > '2026-01-01'，未命中索引

## 分析步骤
1. （第一步：发现的问题现象）网关层监控显示下游接口 `/api/trade/query` 超时率骤升至 92%，同时订单服务线程池满载（100%）且出现大量线程阻塞告警。
2. （第二步：深入排查的过程）向上游追溯依赖链，发现阻塞源头为 `report-service` 定时任务 `report-export` 触发的数据库操作，`db-monitor` 记录到 `t_trade_record` 表锁等待会话数持续攀升至 35 个。
3. （第三步：定位到的具体根因）该定时任务执行的 SQL 语句 `SELECT * FROM ... WHERE create_time > ...` 缺失对应索引，导致 MySQL 进行全表扫描 1200 万行数据并长时间持有表锁，直接拖垮关联业务的连接池与线程池。
4. （第四步：修复措施或建议）DBA 已紧急终止慢查询会话并补建 `idx_create_time` 索引使系统恢复；后续需将报表导出改为分页/异步处理，上线慢 SQL 自动熔断机制，并对核心交易表查询强制要求走索引。
